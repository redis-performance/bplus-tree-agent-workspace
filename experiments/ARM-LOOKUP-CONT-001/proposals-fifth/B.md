# Proposal B: advisory physical-slot hint — NONE

**Choice: NONE for implementation under the current gates.** A hint can be made semantically safe, and a separate per-bucket mode bit permits bounded promotion back to full IDs. I cannot establish that this additional representation and its allocation/lifecycle changes meet the unchanged usable-memory and mutation-guard limits. The simple in-entry marker is incorrect. This is not a proof that every possible advisory design is impossible, and no speed prediction follows.

## Representation evidence

`zbtIndexBucket16` stores eight one-byte tags, the full64-bit home filter and eight16-bit IDs, occupying32bytes; the wide form occupies48bytes (source249–275). The narrow ID accessor maps only65535 to the deleted sentinel; ordinary IDs are decoded without a marker (1798–1824). `zbtIndexReserveLeafId` starts widening near32767 but permits an already-running narrow destination to continue receiving larger IDs, with its emergency boundary at65519 (2197–2219). Thus bit15 is not spare, including in a receiving table. A high ID reused after deletions is also not evidence that a table may reinterpret that bit.

The leaf limit is96 (line144), so a full physical hint needs seven bits. A9-bit leaf ID plus seven-bit slot supports low IDs, but cannot simultaneously encode every legal raw16-bit ID without independent format state. Codes96–126 can denote “no hint”;65535 can remain the tombstone. Those choices solve the small-format sentinels, not the ambiguity with ordinary high IDs. There is no unused seven-byte region in the32-byte bucket, and adding one byte per entry would enlarge the narrow bucket to40bytes before considering any allocator effects:25% more index payload, not a supported <=1% whole-tree claim. Widening to32-bit entries costs50% more narrow-bucket payload.

I also reject borrowing home-filter/tag bits without an explicit filter change. `zbtIndexHomeMayContain`, probe termination, reference finding and scan home-range filtering use these values. Increasing false-positive work or changing emptiness representation is an additional hypothesis with guard exposure, not a free hint channel.

## Bounded alternative considered, not selected

One distinct route avoids a whole-table ID transition: append a mode bitmap to each narrow table allocation, one bit per bucket. For a marked bucket, encode low9-bit ID and high7-bit hint. Before storing any ID>=512 into that bucket, decode at most its eight live entries to raw IDs, preserve tombstones, then clear its mode bit. Never promote that bucket back during its lifetime; a newly allocated receiving table can independently start with hint-capable buckets. Wide tables remain ordinary32-bit IDs. This is a bounded eight-entry local conversion, independent of table length, and supports high IDs, receiving narrow resizes and later free-ID reuse without changing the existing widening thresholds.

The representation still requires changes beyond a scalar hint probe. At B buckets its requested bitmap costs ceil(B/8) bytes, approximately0.391% of narrow bucket payload for sufficiently large B. That arithmetic is **not** a usable-memory result: small-table rounding, actual allocator sizes, two simultaneous resize tables and any descriptor-mode state must all be included. The original allocator adapter reports actual malloc usable size; `zbtIndexTableAlloc` accounts that value (1900–1912), and `zbtTestAllocSize` independently sums live allocations (4640–4653). I will not treat allocator slack or64-bit padding as portable storage, or claim that tiny/empty and transient states satisfy1% from this requested-byte ratio.

An implementation would need separate bucket-span and allocation-span calculations: `zbtIndexOwnsBucket` must exclude a bitmap tail, while `zbtIndexDupTable` must copy it. The current duplication is an exact `zbtIndexTableBytes` allocation/memcpy (2944–2953); memory dismissal uses the same size helper (3019–3026). Fallible reserve overflow checks and defragmentation/allocator ownership must remain valid. A new mode bit in `wide_ids` is unsafe unless every Boolean width consumer is replaced/audited; the source uses it in accessors, allocation, resize selection, reservation and invariant tests. Explicit field layout would need actual32-bit,64-bit and big-endian validation. These are unresolved implementation and memory gates, so this alternative is a future design lead, not the selected hypothesis.

## Required predicate and lifecycle if revisited

Any future hint must be used only after the existing deleted-ID, live-leaf, free-ID and old/new migration checks in `zbtIndexTableFind` (1987–2008). Check hint<count before loading the current physical offset, then use the same full current-record predicate as the ordinary leaf matcher: current tag consistency, external full-hash rejection, packed member decoding, exact binary length and byte equality. A successful match must produce the same logical position and optional score as `zbtScoreLeafFindMember` (1302–1341), including reverse leaves. Every invalid hint or nonmatch falls back to the original complete scan; it never establishes absence. No stored byte offset, external pointer or read-side hint refresh is allowed.

Hints must remain advisory even when apparently fresh. `zbtIndexTableFindReference` explicitly permits interchange of entries sharing tag and leaf ID (2052–2086). `zbtIndexMove` may change any such reachable entry (2387–2447). Consequently a hint cannot identify the logical owner of an index entry, and ZSCAN must continue its existing reference-based disambiguation; it must not enumerate members from hints. In-range stale hints, including a hint now naming another same-tag member, require exact equality and fallback.

Free IDs are reused only when no resize remains (`zbtScoreRegisterLeaf`,825–853). Preserve that rule and the old-table migration guards. Hint invalidation must never substitute for them. Rebuilding, compaction, shifting insertion/deletion, reversal, split and merge may stale positions; accepting this avoids eagerly rewriting every shifted member's index reference. External ownership remains entirely with current leaf records and original accessors.

`zbtIndexCopyLeaf` already iterates all logical positions (2145–2155), so it could populate physical hints without an additional search. Ordinary insertion currently returns only a leaf from `zbtScoreInsert` to `zbtreeInsertNewRaw` (3373–3385), and `zbtIndexInsert` receives only the leaf ID. Getting the new member's final physical slot would require explicitly threading the position through all leaf insertion/rebuild/split results, or leaving a no-hint sentinel. `zbtIndexMove` likewise does not currently receive a member position. I reject an extra member search just to fill a hint and do not assume that population only during rehash gives useful coverage in the fixed500-member fixtures. No retained observation establishes that coverage.

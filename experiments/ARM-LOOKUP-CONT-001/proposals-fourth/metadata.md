## Distinct conditional hypothesis

Within one `zbtIndexTableFind` invocation, after an eligible leaf has returned no match for the immutable `(hash, bytes, length)` query, a later eligible reference to that same leaf cannot turn the negative into a positive: the table-finder loop performs no mutations and leaf IDs are not reused during it. A small local negative-result cache could skip that redundant leaf work. It would preserve the original approximate mask, stored-tag recheck, scalar candidate order, ID decoding, helper boundary, memchr/memcmp, home filter and record representation.

The narrowest form would remember only the last leaf that actually failed, limiting storage to one ID/pointer and validity state. It does not promise to remove nonadjacent repeats separated by another failed leaf. It must be reset for every table-finder call, including each old/new resize table. Cache only after a real eligible negative matcher result, never after a tombstone, out-of-range/free ID or migration rejection. Preserve those original checks/assertions; do not reuse this idea to remove them. An implementation would need to establish whether its comparison can occur without adding work to first-candidate successful hits. No copied scanner, large seen-ID array, heap/global cache, intrinsics, batching, prefetch or fixture-specific branch is proposed.

This changes transient lookup state, not leaf or bucket metadata. Tree-owned bytes and mutation maintenance should be exactly unchanged. Its risk is register lifetime and extra candidate comparisons, especially across the existing out-of-line matcher call. It is conceptually distinct from H1 helper removal, H2 cached score-stream bytes, H4 negative-filter placement and H5 resize dispatch. It does not reuse H7 masks or H8 decoding.

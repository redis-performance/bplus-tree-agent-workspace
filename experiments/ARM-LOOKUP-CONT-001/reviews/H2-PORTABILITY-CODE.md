# Cross-ABI portability harness review

Decision: **CODE REVIEW PASS** for the frozen harness and bounded image-preparation design. This review covers code readiness only. Image construction/receipt and guest correctness require their separately bound operational admissions. H2 remains PARK; this task adds no performance population and grants no source adoption.

The reviewer examined the protocol, input pins, paired metadata oracle, direct refresh-site tests, ABI reporter, compiler wrapper, clock guard, image preparation/receipt scripts, driver and synthetic tests. The reviewer previously implemented a different H2 option, not H2-B or this harness. Only Python synthetic correctness tests and read-only operational checks were performed during this review; no C workload, emulator, build, timing or profiling was run by the reviewer.

The four immutable cells are baseline then H2-B on i686 little-endian ILP32, followed by baseline then H2-B on s390x big-endian LP64. Each retains the original 57 unit tests, all 18 seed/case fixture verifications, 90,000 ordinary and 45,000 external output checks, and the paired 7,693-validation mutation schedule. The two B cells additionally run the unchanged original metadata oracle. The matrix comprises 94 guest invocations, 228 unit tests, 72 fixture verifications and 540,000 supplied output checks. These are intended counts, not executed coverage.

The paired schedule retains insertion, updates, deletion, shrink, alternating edge deletion, duplication, page relocation and append/rebuild coverage, including zero/full-width scores and reversal. Its harness-only direct calls additionally force all four changing refresh sites: leaf build, width-changing in-place insertion, fast insertion with a changed rounded score displacement, and in-place deletion. The 33-to-32 full-width transition changes 272 bytes to 264, exercising both nonzero bytes of the cache under either guest byte order. Each step validates the actual offset pointer, alignment, records and decoded scores; B also checks the cache against the formula. Flags exercise all 256 combinations with the other shared metadata retained. This is deterministic branch coverage, not exhaustive state-space proof.

ABI admission requires exact guest ELF class, byte order and machine, bounded program headers and one safe PT_INTERP. The actual loader resolves inside the target sysroot and is hashed. The runtime reporter binds pointer, size_t, unsigned long, double, uint64, byte-order macros and observed byte order, field sizes/offsets and alignment. B and baseline footprints must match within each ABI. The 64-bit layout remains explicitly constrained; the 32-bit layout is measured rather than invented. Compiler, linker, emulator, packages and sysroot libraries receive receipts. The QEMU CPU policy is fixed to max; missing support stops the attempt. Host ABI is never treated as guest proof.

Compilation uses the exact selected source and frozen referees with assertions enabled. Lookup execution is exclusively verify mode with fixed seeds and count one. A link wrapper aborts on clock_gettime; before guest execution the lookup ELF must define it, have an emitted call to it, and lack unresolved ordinary or 64-bit clock_gettime alternatives. This protects the existing lookup timing entrypoint; it is not a general system-call sandbox. Source hashes and the fixed execution plan supply the broader no-measurement guarantee.

The driver enforces separate image-receipt and correctness reviews, full image content IDs, exact preparation/base labels, source/manifest/review hashes, a generation-bound lease and cleanup implementation. Named containers carry all three exact cleanup labels. Read-only task inputs, no-network correctness containers, CPU selection, memory/pid caps, dropped capabilities and no-new-privileges constrain guest work. Historical unrelated stopped containers are preserved. An interrupted Docker client does not authorize name-based removal; reviewed cleanup retains that responsibility.

Every container is bracketed by source/cleanup identity checks and live isolation checks. Both replacement timer schedules, command hashes, precision and service limits are bound; both retired timers must remain inactive. Coordinator identity, sibling CPU, profiler policy/process absence and absence of other running containers are checked. One fixed task start/deadline now covers preparation and both driver phases; each subprocess is clamped to the remaining task and cleanup margins. The operational deadline does not extend the reservation. The separately reviewed controller must enforce the same deadline during image preparation.

Failures consume the single-use phase and preserve completed rows and raw diagnostics. Baseline failure stops before B and the next ABI; it is an unresolved baseline/ABI/harness limitation. A later B failure after a passing baseline is a candidate correctness failure. There are no adaptive seeds, reduced counts, automatic retries, source repairs or fallback CPU models. Python synthetic tests cover malformed ELF/interpreters, ABI/count/type mismatches, clock alternatives, fixed execution plans, admission labels, timer/cap/retirement drift, deadline clamping, post-failure isolation, a fully mocked matrix and baseline-first failure handling. Mock success is not guest execution evidence.

Limits: no sanitizer run is claimed for these guest cells, QEMU support and real guest builds remain unverified, and passing emulation would cover only the named ABI cases. It supplies no native speed or TMA evidence. No new external consultation was performed by this reviewer; shared consultation has no supporting ABI passage and costs are unknown. Private operational identities and receipts remain outside this report.

## Operational timeout clarification before execution

The subprocess timeout in the frozen driver bounds the Docker client wait; it does not by itself terminate a container process. The code intentionally leaves failed containers to independently reviewed cleanup. Consequently the two-/five-minute guest limits are not yet proven hard guest-process termination bounds. Before operational correctness admission, the controller must either provide a reviewed in-container termination bound or bind immediate cleanup on failure and state the narrower client-wait semantics honestly. The image-preparation launcher is separately being revised to enforce its installation bound inside the container. No execution was admitted while this distinction was unresolved.

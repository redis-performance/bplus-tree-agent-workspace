# Static leaf-search inventory

This is a post-hoc description of already frozen round18 compiler assembly, not a
new preregistered diagnostic or performance result. No compilation or benchmark ran.
[Auditor](audit-round020-static-leaf.py) verifies source assembly hashes and records
every stack access with its line number in [JSON](ROUND-020-STATIC-LEAF-AUDIT.json).

These are the whole zbtScoreLeafFindMember bodies generated by the recorded Apple
Clang17 arm64 C11 O3 build with unchanged debug assertions, allocator and hash code.
Counts include all paths, cold panic branches, prologue/epilogue and callee-save
traffic. They are not executed instruction counts or bytes of linked code. A static
load site can run zero, once or many times. Function frames omit called libc frames,
so the table does not establish peak stack use; it also says nothing about tree-owned
allocations. No cycle, cache, frequency or register-pressure timing cause is inferred.

Removing memchr did not make these compiler-generated leaf bodies smaller or eliminate
stack accesses. That constrains an explanation based only on removing a call, but it
does not explain the single-lane/batched contrast or repair either performance guard.
The existing profiles show changed attribution; the mechanism remains unresolved.
All source decisions and campaign counts remain unchanged.

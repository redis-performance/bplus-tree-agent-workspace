# Independent AMD proposal: libc matching for ordinary scan tags

Author: native AMD worker `/root/aws_amd`, inherited backend/model unknown, token/USD usage unavailable. Written from common packet b1b670c0a and frozen baseline; no Intel/ARM proposal read. This is an actual separate agent proposal. Root chairs after all submissions and fresh A/A.

Hypothesis: use bounded libc `memchr` repeatedly to enumerate physical matches for index tags other than1 inside `zbtLeafTagMatches`, preserving the existing folded0/1 SWAR path. This will reduce timed scan elapsed cost by at least2% at BOTH100K and1M in every discovery/confirmation paired block. Change no hashing, allocator, membership checks, iterator, index tables, or callback behavior.

Evidence: exact matched scoped samples put helper scope21.31–38.99% of100K scan period and23.34–27.93% at1M across three seeds. Census shows mean~69-byte span,~76.6% exactlyone match, only~0.784% tag1; current SWAR scans every8-byte word, tests false-positive byte matches, and runs a scalar tail. Native libc already wins against replacement first-match scanners in related Intel work. This is the opposite substitution in a different helper: scan ALL-match SWAR to libc search, not replacement of existing first-match libc. That precedent is suggestive, not cross-machine timing evidence. Scoped captures have only tens of events each; fractions are approximate and cannot be converted into speed predictions.

Mechanism: long remaining spans can use the host libc implementation for each next match, then advance one physical byte and repeat until bound. Avoid caller-side SWAR word/mask/tail work for ordinary tags. The common single-match case still requires a second miss search unless the match is last; extra calls and short remaining spans may outweigh saved work. No promise that libc uses a particular ISA; inspect actual candidate call sites/library symbol if selected.

Predictions: ordinary sparse tags should benefit most around64–96-byte leaves. Small spans and dense repeated matches may regress because they need many libc calls. Tag1 retains existing code and should have no algorithmic change. Reverse mappings add same logical index transform. External members and resize cases retain subsequent hash/reachability cost, reducing end-to-end fractional gain; memory should be exactly unchanged.

Semantic risks: return every match, exact count, ascending physical order, decreasing logical positions when reversed; tag1 must fold BOTH0 and1, while tag0 helper input remains literal0. Keep count0 no-access semantics and strictly bounded reads. Do not skip trailing search, stop at first hit, sort outputs, or remove genuine collision/reachability checks. No member/score ownership or lifetime changes. Existing original all-match randomized tests and resize/SCAN tests stay frozen. Add only the missing guard-page/zero-span/output-canary/exact-order oracle, plus unchanged scan_interval/wide_scan/live_widen/resize-generation coverage as relevant.

Falsification: fresh A/A failing either primary blocks acceptance; any correctness/sanitizer failure disqualifies implementation; any primary block missing2% improvement rejects it under current strict gate; any demonstrated>1% performance guard or tree-owned-memory regression rejects adoption, unresolved noise or unimplemented guard PARK. Concrete guards must cover all eight baseline operations/five sizes, long keys, small/reversed leaves, folded tag1 and dense same-tag scan patterns. Standard fixture lacks reversed leaves and dense folded tags; correctness tests cannot satisfy missing performance guards. Source remains NONE overnight even if discovery survives. Root independent fresh confirmation and scoped mechanism validation required.

Implementation preference if chair selects: start with the smallest direct bounded `memchr` loop for ordinary tags and untouched fallback. Other isolated implementers may choose distinct call-boundary/tail strategies within this single hypothesis; no combining with decoder or iterator work.
